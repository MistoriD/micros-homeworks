# Домашнее задание к занятию «Микросервисы: подходы» - Шмагин М.Ю.

Вы работаете в крупной компании, которая строит систему на основе микросервисной архитектуры.
Вам как DevOps-специалисту необходимо выдвинуть предложение по организации инфраструктуры для разработки и эксплуатации.

## Задача 1: Обеспечить разработку

Предложите решение для обеспечения процесса разработки: хранение исходного кода, непрерывная интеграция и непрерывная поставка.
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.
Решение должно соответствовать следующим требованиям:

* облачная система;
* система контроля версий Git;
* репозиторий на каждый сервис;
* запуск сборки по событию из системы контроля версий;
* запуск сборки по кнопке с указанием параметров;
* возможность привязать настройки к каждой сборке;
* возможность создания шаблонов для различных конфигураций сборок;
* возможность безопасного хранения секретных данных (пароли, ключи доступа);
* несколько конфигураций для сборки из одного репозитория;
* кастомные шаги при сборке;
* собственные докер-образы для сборки проектов;
* возможность развернуть агентов сборки на собственных серверах;
* возможность параллельного запуска нескольких сборок;
* возможность параллельного запуска тестов.

Обоснуйте свой выбор.

Ответ:

**GitLab SaaS (облачная платформа) + GitLab CI/CD + Self-Hosted GitLab Runners**

### Принципы взаимодействия

* **Управление кодом:** Под каждый независимый сервис выделяется собственный Git-репозиторий в облаке GitLab. В корне репозиториев размещаются манифесты развертывания и файл конфигурации конвейера `.gitlab-ci.yml`.
* **Триггеры и запуск:** Конвейеры активируются автоматически по событиям VCS (push, создание merge request, теги). Также доступен ручной запуск конвейера через веб-интерфейс (`Run pipeline`) с передачей кастомных входных параметров и переменных окружения.
* **Исполнение задач (Runners):** Сборочные задачи делегируются собственным агентам (Self-Hosted Runners), развернутым во внутреннем контуре инфраструктуры. Агенты запускают изолированные Docker-контейнеры на базе кастомных образов, выполняют этапы сборки и тестирования, а готовые артефакты отправляют во встроенный реестр (GitLab Container Registry).
* **Конфигурация и безопасность:** Секреты, токены и пароли изолируются с помощью механизмов GitLab CI/CD Variables (с маскированием значений и защитой по веткам/окружениям) либо подтягиваются динамически через интеграцию с внешним HashiCorp Vault. Параметры конкретной сборки гибко управляются директивами `rules`, матричными сборками (`parallel:matrix`) и подключаемыми шаблонами (`include`).

### Обоснование выбора

GitLab представляет собой законченную платформу, исключающую необходимость интеграции и поддержки зоопарка сторонних утилит. Механизм шаблонизации (`ci/templates`) позволяет стандартизировать типовые процессы CI/CD для десятков микросервисов компании. Подключение собственных раннеров гарантирует безопасность корпоративного контура и гибкое выделение вычислительных ресурсов под тяжелые этапы. Встроенные средства матричного выполнения и шардирования обеспечивают эффективный параллельный запуск тестов, а зрелые механизмы управления переменными и интеграция с Vault закрывают требования безопасности корпоративного уровня.

## Задача 2: Логи

Предложите решение для обеспечения сбора и анализа логов сервисов в микросервисной архитектуре.
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.
Решение должно соответствовать следующим требованиям:

* сбор логов в центральное хранилище со всех хостов, обслуживающих систему;
* минимальные требования к приложениям, сбор логов из stdout;
* гарантированная доставка логов до центрального хранилища;
* обеспечение поиска и фильтрации по записям логов;
* обеспечение пользовательского интерфейса с возможностью предоставления доступа разработчикам для поиска по записям логов;
* возможность дать ссылку на сохранённый поиск по записям логов.

Обоснуйте свой выбор.

Ответ:

**Fluent Bit ➔ Apache Kafka ➔ Grafana Loki ➔ Grafana**

### Принципы взаимодействия

* **Сбор данных:** На узлах кластера в качестве легковесного агента разворачивается Fluent Bit. Он перехватывает стандартные потоки вывода (`stdout`/`stderr`) контейнеров без внедрения в кодовую базу приложений.
* **Буферизация и надежность:** Fluent Bit сохраняет входящий поток во встроенный дисковый буфер и передает данные в распределенный брокер Apache Kafka. Брокер сообщений нивелирует пиковые нагрузки и защищает систему от потери логов при временных сбоях сети или недоступности хранилища.
* **Индексация и хранение:** Grafana Loki вычитывает сообщения из топиков Kafka. В отличие от тяжелых поисковых движков, Loki индексирует исключительно метаданные (лейблы), а сами сжатые чанки логов складывает в масштабируемое блочное или объектное хранилище (S3-совместимое).
* **Пользовательский интерфейс и разграничение прав:** Grafana выступает единой точкой входа для команд разработки и эксплуатации. Поиск и агрегация выполняются через язык запросов LogQL. Платформа поддерживает ролевую модель доступа (RBAC) для изоляции сред и позволяет делиться прямыми ссылками на сохраненные выборки, фильтры и временные диапазоны.

### Обоснование выбора

Данный стек сочетает минимальную ресурсоемкость и устойчивость к высоким нагрузкам:

* **Экономичность инфраструктуры:** Отказ от тотального полнотекстового индексирования (характерного для OpenSearch/ELK) в пользу индексной модели Loki кардинально сокращает затраты на дисковые массивы и оперативную память.
* **Гарантированная сохранность:** Буфер на стороне Fluent Bit в связке с реплицируемыми топиками Kafka полностью исключает потерю сообщений при масштабных всплесках трафика или регламентных работах на бэкенде.
* **Единая рабочая среда:** Инженерам не требуется переключаться между разрозненными инструментами — журналы событий, графики метрик и трассировки доступны в интерфейсе Grafana, с поддержкой шаринга ссылок на конкретные инциденты.

## Задача 3: Мониторинг

Предложите решение для обеспечения сбора и анализа состояния хостов и сервисов в микросервисной архитектуре.
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.
Решение должно соответствовать следующим требованиям:

* сбор метрик со всех хостов, обслуживающих систему;
* сбор метрик состояния ресурсов хостов: CPU, RAM, HDD, Network;
* сбор метрик потребляемых ресурсов для каждого сервиса: CPU, RAM, HDD, Network;
* сбор метрик, специфичных для каждого сервиса;
* пользовательский интерфейс с возможностью делать запросы и агрегировать информацию;
* пользовательский интерфейс с возможностью настраивать различные панели для отслеживания состояния системы.

Обоснуйте свой выбор.

Ответ:

**Prometheus-стек (Node Exporter + cAdvisor + Prometheus Client Libraries) ➔ Prometheus TSDB ➔ Grafana**

### Принципы взаимодействия

* **Метрики операционной системы:** На каждом физическом или виртуальном сервере запускается Node Exporter, транслирующий показатели утилизации процессорных мощностей, оперативной памяти, дисковых подсистем и сетевых интерфейсов.
* **Метрики контейнеризированной среды:** Агент cAdvisor отслеживает потребление аппаратных ресурсов на уровне каждого запущенного контейнера и микросервиса.
* **Прикладные метрики:** Сервисы подключают клиентские библиотеки (`Prometheus Client Library`) и отдают бизнес-показатели, данные о задержках (latency) и коды ответов через защищенный эндпоинт `/metrics`.
* **Сбор и агрегация:** Сервер Prometheus выполняет сбор телеметрии по pull-модели через механизмы динамического обнаружения сервисов (Service Discovery) и сохраняет временные ряды во встроенной TSDB.
* **Визуализация и алертинг:** Grafana подключается к Prometheus в качестве источника данных. Пользователи конструируют аналитические дашборды, применяя функции языка PromQL для вычисления производных метрик, агрегации данных и настройки правил оповещения.

### Обоснование выбора

Связка Prometheus и Grafana — индустриальный стандарт для распределенных микросервисных систем:

* **Комплексная наблюдаемость (Observability):** Достигается корреляция между состоянием аппаратных ресурсов узла, нагрузкой от конкретного контейнера и поведением бизнес-логики приложения в рамках одного дашборда.
* **Стабильность pull-архитектуры:** Опрос сервисов сервером мониторинга гарантирует предсказуемую нагрузку на сеть и предотвращает каскадный отказ системы телеметрии при лавинообразном росте трафика.
* **Развитая экосистема:** Доступен широкий выбор готовых экспортеров под инфраструктурные компоненты (СУБД, очереди сообщений, балансировщики) и обширная библиотека преднастроенных дашбордов Grafana.
* **Горизонтальная масштабируемость:** При значительном росте объема метрик архитектура безболезненно расширяется за счет добавления решений для долгосрочного хранения (VictoriaMetrics или Thanos).
