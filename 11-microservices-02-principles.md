# Домашнее задание к занятию «Микросервисы: принципы» - Шмагин М.Ю.

Вы работаете в крупной компании, которая строит систему на основе микросервисной архитектуры.
Вам как DevOps-специалисту необходимо выдвинуть предложение по организации инфраструктуры для разработки и эксплуатации.

## Задача 1: API Gateway

Предложите решение для обеспечения реализации API Gateway. Составьте сравнительную таблицу возможностей различных программных решений. На основе таблицы сделайте выбор решения.

Решение должно соответствовать следующим требованиям:

* маршрутизация запросов к нужному сервису на основе конфигурации,
* возможность проверки аутентификационной информации в запросах,
* обеспечение терминации HTTPS.

Обоснуйте свой выбор.

| Параметр | Nginx | Traefik | Kong Gateway |
| --- | --- | --- | --- |
| **Маршрутизация по конфигурации** | Статические файлы `.conf`, для применения правок нужен reload процесса | Автоматический service discovery через интеграции с оркестраторами (Docker, K8s) | Декларативная модель управления, динамическое обновление маршрутов через Admin API без перезапуска |
| **Проверка аутентификации** | Минимальный базовый функционал, требует написания Lua-скриптов или внешних модулей | Встроенная поддержка базовых сценариев (ForwardAuth, JWT, Basic Auth, OAuth2/OIDC) | Богатая экосистема готовых плагинов из коробки (Key Auth, JWT, OAuth 2.0, OpenID Connect, mTLS, LDAP) |
| **Терминация HTTPS** | Стандартная реализация, сертификаты подключаются статически, автообновление через cron/certbot | Нативная интеграция с Let's Encrypt / ACME с автоматическим выпуском и ротацией | Полная поддержка TLS 1.2/1.3, SNI, динамическая загрузка сертификатов и нативная связка с cert-manager |

Ответ:

Выбранное решение: **Kong Gateway**

Обоснование: Продукт полностью закрывает поставленные требования без необходимости разработки собственной обвязки или написания вспомогательного кода. Наличие развитой экосистемы плагинов безопасности снимает задачу валидации токенов с микросервисов, а механизм динамической конфигурации идеально встраивается в автоматизированные пайплайны CI/CD.

## Задача 2: Брокер сообщений

Составьте таблицу возможностей различных брокеров сообщений. На основе таблицы сделайте обоснованный выбор решения.

Решение должно соответствовать следующим требованиям:

* поддержка кластеризации для обеспечения надёжности,
* хранение сообщений на диске в процессе доставки,
* высокая скорость работы,
* поддержка различных форматов сообщений,
* разделение прав доступа к различным потокам сообщений,
* простота эксплуатации.

Обоснуйте свой выбор.

| Параметр | Apache Kafka | RabbitMQ | Apache Pulsar |
| --- | --- | --- | --- |
| **Кластеризация** | Распределенная архитектура, репликация партиций, поддержка ISR, автоматический выбор лидера | Кластеризация на базе Quorum Queues (алгоритм Raft) и классических зеркалированных очередей | Разделение слоев: уровень брокеров (stateless) и уровень хранения Apache BookKeeper |
| **Хранение на диске** | Неизменяемый распределенный лог (Commit Log) на диске, конфигурируемые политики retention | Запись на диск для durable-очередей при вытеснении из RAM или для сохранения гарантий доставки | Многоуровневое хранение (Tiered Storage) в BookKeeper с возможностью сброса долгоживущих данных в S3 |
| **Высокая скорость** | Экстремальная пропускная способность за счет последовательного ввода-вывода (Sequential I/O) и механизма zero-copy (от сотен тысяч до миллионов сообщений/сек) | Стабильная производительность при сложной маршрутизации, но ограниченная пропускная способность на больших потоках (~50–100K сообщений/сек) | Высокая пропускная способность с низкой задержкой, сопоставимая с Kafka, но с дополнительными сетевыми накладными расходами между слоями |
| **Поддержка форматов** | Агностицизм к полезной нагрузке (байтовые массивы), опциональный строгий контроль контрактов через Schema Registry (Avro, Protobuf, JSON) | Поддержка любых бинарных и текстовых форматов данных, маршрутизация опирается на AMQP-заголовки | Встроенная поддержка схем (Schema Registry) прямо на уровне брокера, валидация эволюции контрактов |
| **Разделение прав (ACL)** | Авторизация на базе ACL (чтение/запись на уровне топиков и групп), интеграция с Kerberos, LDAP, Apache Ranger | Гибкая ролевая модель, гранулярные права (`read`, `write`, `configure`) в контексте vhost, exchange и queue | Мультитенантность из коробки, разграничение прав на уровне tenants, namespaces и отдельных топиков |
| **Простота эксплуатации** | Значительно упростилась с переходом на протокол KRaft (устранен ZooKeeper), доступны готовые Kubernetes-операторы (Strimzi) | Высокая: единый бинарный сервис, интуитивный Web UI управления, низкий порог входа для развертывания и базовой поддержки | Высокая сложность: необходимость отдельного администрирования пула ZooKeeper, нод BookKeeper и брокеров Pulsar |

Ответ:

Для реализации проекта выбрана **Apache Kafka**.

Обоснование: Платформа оптимально удовлетворяет всем ключевым требованиям надежности и производительности крупного микросервисного ландшафта. Архитектурный переход на кворум KRaft исключил внешнюю зависимость от ZooKeeper, существенно снизив операционную сложность развертывания и мониторинга. Механизм последовательной записи на диск гарантирует сохранность сообщений без потери скорости передачи данных, а развитые средства ACL обеспечивают изолированный доступ к топикам для разных команд и сервисов.
